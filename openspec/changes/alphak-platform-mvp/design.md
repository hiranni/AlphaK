# Design

## Context

AlphaK 规划时是绿地项目；当前仓库已有一个 Rust/Axum + SQLite + Vite/React 的演示垂直切片，尚未接入真实数据源。MVP 需要先明确「当前切片」「完整 MVP 目标」与「V1 能力」三种交付状态，避免验收口径混用。约束来自 `docs/requirements-analysis.md` 与 `docs/specs/README.md`：不做全市场扫描、不接实盘、默认本地单用户、所有数据需标注来源与时间。

## Implementation Override (applied)

用户明确要求后端改为 Rust，前端可自行选择；项目直接本机运行，不需要 Docker，也不引入其他数据库。因此本次实现采用以下 MVP 垂直切片：

- 后端：Rust + Axum + rusqlite（SQLite）；不依赖其他数据库。
- 前端：Vite + React 19 + TypeScript + 手写 Hallmark tokens/CSS，替代 Next.js + Tailwind。
- 数据：默认确定性演示种子；已接入腾讯/东财公开源的小样本日线、快照与指数同步，来源/批次/新鲜度可追溯。
- 不引入 Redis/Worker/Docker；MVP 使用 SQLite 与单进程调度。
- 这一偏差已在 `README.md` 与实现中标注，避免把演示切片误认为生产实现。

### 交付状态

| 状态 | 技术栈 | 验收口径 |
| --- | --- | --- |
| 当前切片 | Rust/Axum + SQLite；Vite/React | `cargo test`、`npm run build`、演示种子 + 公开源小样本同步、本地回环 |
| 完整 MVP 目标 | Rust/Axum + SQLite；直接本机进程 | 真实数据源、质量闸门、30 分钟可用、异步回填 |
| V1 | 股票池/回测/虚拟盘/Agent/回放 | 独立 change，另行验收 |

**FastAPI/其他数据库不再恢复**：用户已指定 Rust + SQLite；不引入 PostgreSQL/Redis/Docker。

## Goals / Non-Goals

**Goals:**

- 用一套可本地启动的模块化单体交付 MVP，避免过早拆分微服务。
- 建立可替换的数据源适配层与幂等同步任务，覆盖行情、财务、指数/板块、每日基础指标与公司资料，支撑后续股票池、回测、虚拟盘与 Agent。
- 让行情、图表、财务查询在本地单机达到可用的响应速度。
- SQLite 是唯一事实来源；snapshot 只做读加速。
- 保持与 `docs/specs` 契约兼容：证券代码、8 只上限、禁全市场扫描等边界在未来 change 中可直接复用。

**Non-Goals:**

- 不实现股票池、回测、虚拟盘、Agent 执行、可解释回放、多用户权限。
- 不实现实时逐笔、Tick 级行情、分钟级撮合或券商接口。
- 不实现全市场条件选股、排名或批量扫描。
- 不提供桌面客户端、移动原生 App 或公网 SaaS 计费。

## Decisions

### 1. 模块化单体 + 独立采集 Worker

**选择**：MVP 用一个 Web/API 进程内的调度循环执行同步任务；V1 需要隔离长任务时再拆独立 Worker。

**理由**：本地单用户 MVP 的同步任务很短，单进程足够；拆分 Worker/Redis 会增加没有必要的运维面。

**备选**：独立 Worker（任务真的变长后再考虑）；一开始拆微服务（过度设计）。

### 2. 技术栈：Rust/Axum + Vite/React + SQLite

**选择**：
- 前端：Vite + React 19 + TypeScript + 手写 Hallmark tokens/CSS；K 线用 TradingView Lightweight Charts；数据请求用原生 fetch。
- 后端：Rust + Axum + rusqlite；指标在 Rust 内计算。SQLite 是唯一数据库。
- 存储：SQLite 单文件，适合本地单用户 MVP。
- 缓存/队列：单进程调度 + SQLite snapshot，不引入 Redis/Worker。
- 部署：本机 `cargo run` + `npm run dev`，不需要 Docker。

**理由**：用户明确指定后端 Rust；Vite/React 足够支撑研究工作台，Hallmark tokens 便于做非模板化界面。SQLite 让无 Docker 环境也能先验证领域模型。

**备选**：Next.js（SSR 对本 MVP 非必需）；FastAPI（已否决）；ClickHouse（MVP 运维过重）。

### 3. 数据模型与分区

**选择**：核心表 `instrument`、`trading_calendar`、`quote_daily`、`financial_report`、`financial_indicator`、`index_catalog`、`index_quote`、`index_member`、`sector_catalog`、`sector_member`、`daily_basic`、`company_profile`、`sync_job`、`data_quality_report`。`quote_daily` 以 `(symbol, trade_date)` 唯一，按年分区；`index_quote` 以 `(index_code, trade_date)` 唯一；`daily_basic` 以 `(symbol, trade_date)` 唯一；`financial_report` 以 `(symbol, report_period, statement_type, version)` 唯一；`version` 单调递增、`supersedes` 指向上一版、`announce_date`/`effective_at` 与 `payload_hash` 保留，更正/重述只新增版本，不覆盖旧版本。

**理由**：唯一约束保证重复同步幂等；按年分区控制单表体积；`announce_date` 是后续 point-in-time 回测的基础。

**备选**：只建宽表（查询简单但财务口径混乱）；把行情放对象存储（MVP 查询复杂）。

### 4. 数据源适配器与数据集级主备

**选择**：定义统一适配器与 DTO，但**按数据集配置主备**，不做一条通用 fallback 链。首批只接行情三类数据：

| 数据集 | 主源 | 备源 | 首批范围 |
| --- | --- | --- | --- |
| 个股日线 | 腾讯（实测后调整） | 东方财富 | 3 只样本 × 最近 5 个交易日 |
| 行情快照 | 腾讯（实测后调整） | 东方财富 | 同上股票 + 2 个指数 |
| 指数日线/快照 | 腾讯（实测后调整） | 东方财富 | 上证指数、沪深 300 |

- 新浪作为第三校验源，不进入首批主备链；巨潮用于财务/公告，通达信后续评估。
- 每个源独立实现 HTTP 客户端、限频、超时、重试、来源冷却和字段校验。
- 主源失败时只切该数据集的备源，不跨数据集复用备用链。
- 小样本实测比较日期、OHLC、成交量单位、收盘价容差和故障切换后，再确定默认主备优先级。
- AxData 只作为公开 endpoint/字段参考，不引入 Python 运行时或 DuckDB/Parquet；其许可证为 Research-Only，不复制源码。

**理由**：不同数据集的可信源、更新时间和字段口径不同；数据集级主备能避免“一个源挂了把无关数据集也切走”，也便于逐项验收。

**备选**：一条全局 fallback 链（会跨数据集污染）；只接单源（无法满足可用性）；直接引入 AxData（增加 Python 与额外数据库依赖）。

### 5. 同步策略：增量优先、幂等写入、质量闸门

**选择**：交易日 15:10 按日历增量拉取，目标 17:00 前完成（收盘后 2 小时）；18:00 只做对账与补漏。先写 staging，质量检查通过后写入正式表；行情按唯一键幂等 upsert，财务按版本追加（不覆盖历史），失败重试 3 次并保留断点。全量初始化只在首次或人工触发时执行。数据源晚发布时从源可用时刻重新计时并标注“等待数据源”。

**理由**：免费源限频，全量重跑成本高；staging + 质量闸门避免坏数据污染图表。

**备选**：直接写正式表（简单但异常数据难回滚）；每次全量覆盖（慢且浪费配额）。

### 6. 市场概览用预聚合 + 缓存

**选择**：日线同步完成后计算市场宽度、板块涨跌与指数快照，写入 `market_snapshot` 预聚合表；API 优先读 snapshot，支持强制刷新。

**理由**：首页不能每次请求都扫描全市场日线；预聚合把计算放在收盘后，符合“不做请求时全市场扫描”的边界。

**备选**：请求时实时聚合（慢且可能触发全表扫描）；只做纯前端缓存（多端不一致）。

### 7. 图表与指标计算放后端

**选择**：K 线接口返回 OHLCV 与复权因子，指标默认由后端计算并缓存；前端只负责渲染与交互。指标计算使用统一函数库，固定样本回归测试。

**理由**：保证前后端、不同页面口径一致；后续回测与虚拟盘可复用同一套指标实现。

**备选**：前端计算（实现快但多处重复、难校验）；引入第三方指标服务（MVP 不需要）。

### 8. API 契约：REST + OpenAPI + 统一错误

**选择**：`/api/v1` REST，OpenAPI 自动生成；统一响应 `{code, message, data, request_id}`；分页 `page/page_size`；时间 ISO 8601；错误码稳定。

**理由**：前后端分离、易测试、后续 Agent 工具层可直接复用。

**备选**：GraphQL（灵活但 MVP 增加复杂度）；tRPC（TypeScript 单体方便，但 Python 数据层不匹配）。

### 9. 本地安全边界

**选择**：MVP 固定本地单用户，默认且只允许绑定 `127.0.0.1`；请求监听非回环地址时拒绝启动。密钥只从环境变量或服务端加密配置读取；日志统一脱敏。远程访问与认证放到后续 change。

**理由**：MVP 不做完整多用户，但不能把“本地”当成“无安全”。

**备选**：默认无认证且监听 `0.0.0.0`（不可接受）；MVP 就做登录/多用户（超出范围）。

### 10. 备份与恢复

**选择**：`pg_dump` + 配置文件打包；备份文件带 SHA-256；恢复前先备份当前状态并校验备份；迁移前自动备份。

**理由**：自托管产品必须有可恢复路径；恢复失败不能破坏现有数据。

**备选**：只依赖单文件复制（容易漏 WAL）；云备份（MVP 不强制）。

### 11. 前端信息架构

**选择**：顶部全局搜索 + 左侧导航（首页/自选/数据管理/设置）；首页使用卡片网格，指数/板块卡片可进入详情；个股页使用头部行情 + 页签（概览/K 线/财务/公司资料）。

**理由**：符合桌面浏览器优先、信息密度高的研究场景；移动端只做可用性适配，不做独立 App。

**备选**：单页工作台（信息拥挤）；移动优先（MVP 用户主要在桌面研究）。

### 12. 参考数据与每日基础指标

**选择**：新增 `market-reference-data` 能力，拥有指数目录/行情/成分、板块目录/成员、`daily_basic`（股本、市值、PE/PB）与 `company_profile`。参考数据走与行情相同的适配器、staging、质量闸门与任务框架，但独立生成覆盖率报告。

**理由**：市场概览和个股研究依赖这些数据，但它们的更新频率、来源和缺失语义与日线不同；独立能力可以避免 `market-data` 变成无边界的“所有数据”模块。

**备选**：全部塞进 `market-data`（简单但边界模糊）；请求时从数据源实时查（慢且不稳定）。

### 13. OpenAPI-first 与 TypeScript client

**选择**：后端以 OpenAPI 为契约源，CI 生成 TypeScript client；前端只通过生成 client 调 API；增加契约测试，校验后端 Schema 与前端调用一致。

**理由**：MVP 页面与接口较多，手工维护类型会漂移；生成 client 能让字段缺失在编译期暴露。

**备选**：手写 fetch 封装（快但易漂移）；GraphQL（MVP 增加复杂度）。

### 14. 可观测性

**选择**：结构化日志 + 请求/任务指标 + 错误追踪（Sentry 或 OpenTelemetry 任一，按团队熟悉度选）；关键失败（同步、健康检查、备份恢复）产生告警。日志与指标统一脱敏。

**理由**：NFR-13 要求错误追踪，单机自托管也需要可诊断；不能只靠 `console.log`。

**备选**：只写文件日志（难以定位性能与失败趋势）；完整 APM（MVP 过重）。

### 15. 初始化两阶段

**选择**：启动阶段只保证应用、数据库、最近交易日数据与证券列表可用（≤30 分钟）；近 10 年日线与财务由后台回填任务分批执行，页面显示进度，可断点续跑。首次首页允许展示“历史回填中”。

**理由**：免费数据源限频，10 年全量无法稳定在 30 分钟内完成；把“可用”和“全量”分开，验收才可执行。

**备选**：启动时阻塞等待全量（首次体验差且易失败）；只导入最近一年（不满足研究需求）。

### 16. 行情双源接入与失败语义

**选择**：首批实现 `eastmoney` 与 `tencent` 两个 Rust HTTP 客户端，覆盖个股日线、快照与指数数据。每次任务生成 `batch_id`；先校验再事务写入，记录 `source`、`batch_id`、`fetched_at`。不复权 OHLCV 与复权因子分开存储，复权因子单独记录来源与批次。发布范围严格限定为本次任务请求的 symbol/date；不晋升旧批次、不越过请求范围。

失败语义：

- 单个源超时/5xx/字段缺失：限时重试，仍失败则标记该源失败并进入冷却；
- 主源失败：切该数据集备源；备源成功则任务部分成功，并记录主/备来源；
- 两源均失败：任务失败，保留最后成功数据，数据管理页/行情页显示“已过期”，**禁止自动回退 mock 或演示种子**；
- 网络失败不删除旧数据；后续按退避自动重试，也可手动触发。

**理由**：免费公开接口不稳定；必须把“数据是否最新”和“数据是否可用”分开，不能把旧数据标成最新。

**备选**：失败时回退 mock（会污染研究结论）；全部或全无（一个小缺口导致整个页面不可用）。

### 17. 数据源参考与许可边界

**选择**：参考 AxData 已封装的东财、腾讯、新浪、巨潮、交易所接口清单，独立实现 Rust 请求与解析；不安装 AxData，不复制其源码，不引入其存储层。AlphaK 定位个人研究/非商业用途；公开接口仍需遵守上游 ToS、限频与再分发约束。

**理由**：满足“开源免费、纯 Rust + SQLite、不新增 Python/DuckDB”的约束，同时保留可追溯的接口来源。

**备选**：直接依赖 AxData（Python 3.11+、Research-Only、额外存储）；完全自研所有源（成本过高）。

### 18. 部署网络边界

**选择**：API 只绑定 `127.0.0.1`；不提供 Docker/远程访问路径。

**理由**：本地 MVP 的安全边界是宿主机回环；不引入容器网络复杂度。

**备选**：后续远程访问（需要登录/TLS，另行设计）；直接发布 API 到局域网（不符合 MVP 边界）。

**状态**：直接本机进程运行。

## Risks / Trade-offs

- **免费公开接口限频、反爬或字段变更** → 数据集级主备、超时/重试/冷却、录制 fixture、把“数据截至时间”作为产品能力而不是异常。
- **上游 ToS/许可风险** → 个人研究/非商业使用；逐项核对限频与再分发限制，不把公开接口当成官方授权。
- **全市场日线初始化耗时长** → 分批导入、断点续传、进度可见；首次启动允许先展示部分数据。
- **SQLite 单文件损坏/磁盘不可用** → 备份恢复 + integrity_check；不引入其他数据库作为回退。
- **指标计算口径不一致** → 固定样本回归测试、公式文档化、后端单一实现。
- **预聚合与原始数据不一致** → 以原始日线为准，预聚合可重算；质量报告暴露差异。
- **本地模式被误暴露到公网** → 只允许回环绑定，非回环直接拒绝启动，启动日志打印绑定地址。
- **范围蔓延到 V1** → 路由与导航不暴露未实现能力；未实现接口返回明确“未开放”，不用假数据占位。
- **图表库性能不足** → 5 年日线做降采样与分段加载；保留 ECharts 作为统计图备选。
- **参考数据缺失或口径不一致** → 独立覆盖率报告、缺失显示“—”、抽样对账、人工修正留痕。
- **10 年回填耗时或中断** → 两阶段初始化、分批、断点续传、进度可见、可重试。
- **OpenAPI 与前端类型漂移** → 生成 TypeScript client + 契约测试。

## Migration Plan

1. 绿地初始化：创建数据库、迁移、种子数据（证券列表、交易日历、指数配置）。
2. 首次启动：导入证券列表、日历、最近交易日行情、指数/板块/每日基础指标/公司资料，30 分钟内可用；近 10 年日线由后台回填，失败可断点续跑。
3. 上线 MVP：健康检查通过、首页与个股页可用后开放使用。
4. 回滚：保留上一版本镜像与数据库备份；迁移失败时恢复备份并回退镜像。
5. 后续 change：股票池/回测/虚拟盘/Agent/回放复用本设计的 `instrument`、`quote_daily`、`daily_basic`、`trading_calendar`、参考数据与适配器层，不重写数据底座。

## Open Questions

- ~~MVP 首个数据源是否只做 AkShare？~~ 已否决：MVP 改为开源免费多源，按数据集主备；首批腾讯主/东财备，覆盖日线、快照与指数。
- ~~默认主备顺序是否最终固定为“东财主、腾讯备”？~~ 小样本实测中腾讯稳定返回，东财日线/快照出现 `Empty reply from server`；暂定“腾讯主、东财备”，东财恢复后再复核。
- 参考数据中概念板块是否首版必须？当前设计按“行业必做、概念可得时提供”推进。
